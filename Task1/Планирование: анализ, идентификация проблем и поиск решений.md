# Планирование: анализ, идентификация проблем и поиск решений

## 1. Что видно на схеме

- Три приложения: онлайн-магазин, CRM и MES. У каждого по одному инстансу на EC2.
- Shop API и CRM API работают с одной базой — Shop DB.
- CRM и MES обмениваются сообщениями через RabbitMQ.
- 3D-файлы лежат в S3, их используют Shop API, CRM API и MES API.
- Партнёры (API users) ходят напрямую в MES API. Заказ в CRM появляется только после сообщения от MES.
- MES считает цену 2–3 минуты, иногда до 30 минут.
- Мониторинга, логов и трейсинга нет.

## 2. Проблемы

### Существующие

1. Заказы "теряются" и висят месяцами. Производство справляется, значит заказы застревают где-то между системами (магазин → CRM → MES → CRM). Где именно — никто не знает, потому что нет мониторинга, логов и трейсинга.
2. Сообщения в RabbitMQ могут теряться. Не видно DLQ, повторных попыток, подтверждений обработки. Если CRM или MES упали во время обработки сообщения, статус заказа просто не поменяется.
3. Расчёт цены долгий и выполняется прямо в MES API. Тяжёлые расчёты забирают ресурсы единственного инстанса, и из-за этого тормозит всё остальное в MES.
4. Партнёры не получают заказы. Скорее всего, запрос висит, пока считается цена, падает по таймауту, и заказ не доходит до CRM. Партнёр при этом не знает, создан заказ или нет.
5. Медленный дашборд в MES. Фильтр и пагинация не помогли. Вероятные причины: тяжёлые запросы к MES DB (нет индексов по статусу и дате, OFFSET-пагинация по большой таблице) и общая загрузка MES API расчётами.
6. Долгие релизы. E2E-тесты прогоняются вручную одним QA, деплой в release и prod ручной. Исправления доходят до прода больше месяца.

### Потенциальные

7. Единые точки отказа: по одному инстансу каждого приложения, одна база на чтение и запись, один RabbitMQ. Падает любой компонент — встаёт часть процесса.
8. Нагрузка растёт (+100 заказов в месяц плюс заказы по API), а горизонтального масштабирования нет.
9. Общая база у магазина и CRM. Изменение схемы может сломать сразу два приложения, их сложно разрабатывать и релизить отдельно.
10. Открытый API без защиты: нет API Gateway и ограничения запросов. Один крупный партнёр может положить MES для всех.
11. Нет места, где виден полный статус заказа. Статусы меняются в трёх системах, и каждая знает только свою часть.
12. Команда: на C# (MES) всего один разработчик. Если он уйдёт, MES некому поддерживать. Автотестами тоже никто не занимается.
13. S3 и базы растут (3D-модели тяжёлые), политики хранения нет.

## 3. Инициативы

1. Мониторинг — метрики с API, баз и RabbitMQ (Prometheus + Grafana), алерты.
2. Трейсинг — OpenTelemetry + Jaeger, чтобы видеть путь заказа через магазин, CRM и MES.
3. Логирование — централизованный сбор логов (ELK/OpenSearch), обязательно логировать смену статусов заказа.
4. Надёжные сообщения — durable-очереди, persistent-сообщения, ручной ack, DLQ, повторные попытки, идемпотентная обработка.
5. Асинхронный расчёт цены — вынести расчёт из MES API в отдельные воркеры, которые берут задачи из очереди.
6. Асинхронный API для партнёров — сразу отдавать номер заказа, статус партнёр узнаёт запросом или через webhook.
7. API Gateway — аутентификация партнёров, rate limiting, квоты.
8. Ускорение дашборда MES — индексы, keyset-пагинация, кеш списка заказов (Redis).
9. Масштабирование — минимум 2 инстанса каждого API за балансировщиком, read-реплика для MES DB, кластер RabbitMQ.
10. Автотесты и CI/CD — автоматизировать основные E2E-сценарии (QA уже хочет этим заниматься), автодеплой в release.
11. Разделение Shop DB — своя база у магазина и у CRM, обмен через события.
12. Найм — второй C#-разработчик, QA-автоматизатор (или обучить текущего QA).

## 4. Приоритеты

Сначала понять, где теряются заказы, потом перестать их терять, потом ускорять и масштабировать.

1. Мониторинг, логирование, трейсинг (1, 2, 3) — без них мы чиним вслепую и не можем показать бизнесу результат.
2. Надёжные сообщения (4) — недорого и сразу уменьшает потерю заказов.
3. Асинхронный расчёт цены и асинхронный API (5, 6) — главная причина тормозов MES и проблем у партнёров.
4. Ускорение дашборда MES (8) — жалобы операторов.
5. API Gateway (7) — защита от перегрузки со стороны партнёров.
6. Автотесты и CI/CD (10) — ускорят релизы всех остальных доработок.
7. Масштабирование (9) — имеет смысл после выноса расчётов, иначе новые инстансы тоже забьются.
8. Разделение Shop DB (11) — дорого, текущих жалоб не решает, оставляем на потом.

Найм (12) запускаем сразу, параллельно со всем остальным, потому что он занимает много времени.

## 5. Целевая архитектура через полгода

- Партнёры ходят через API Gateway с ограничением запросов.
- MES API только принимает заказы и отдаёт данные операторам. Цену считают отдельные воркеры, которые читают задачи из RabbitMQ. Если заказов много — добавляем воркеров.
- RabbitMQ настроен надёжно: DLQ, повторные попытки, подтверждения. Повторное сообщение не создаёт дубль заказа.
- Партнёр сразу получает номер заказа, а статус узнаёт через webhook или запрос.
- Дашборд MES открывается быстро: индексы, кеш в Redis, чтение с реплики.
- Каждый API работает минимум в двух экземплярах.
- Есть мониторинг, логи, трейсинг и алерты. По номеру заказа видно, где он сейчас.
- Основные сценарии покрыты автотестами, релизы выходят раз в две недели без задержек на месяц.

Общая Shop DB пока остаётся — это следующий этап.

## 6. Если можно сделать только три пункта

1. Мониторинг и трейсинг заказа (вместе с логами). Сейчас мы не знаем точно, где пропадают заказы. Всё остальное без этого — догадки, и улучшения нечем измерить.
2. Асинхронный расчёт цены в отдельных воркерах и асинхронный ответ партнёрам. Это снимает основную нагрузку с MES API: перестанет тормозить дашборд, перестанут падать запросы партнёров. Именно из-за этого компания теряет крупные контракты.
3. Надёжная доставка сообщений в RabbitMQ (DLQ, повторные попытки, идемпотентность). Задача небольшая, но она напрямую закрывает потерю заказов между CRM и MES.

Почему не остальное:
- Кеш дашборда — после выноса расчётов MES API разгрузится, и, возможно, хватит индексов. Если нет — это следующий шаг.
- Автотесты важны, но QA может начать их постепенно и без отдельной инициативы.
- Масштабирование без асинхронного расчёта мало что даст.
- Разделение базы — дорого и не решает текущие жалобы клиентов.
