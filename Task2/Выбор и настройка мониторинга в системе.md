# Выбор и настройка мониторинга в системе

## 1. Мотивация

Сейчас мониторинга нет. Яндекс Метрика видит только сайт магазина, а заказы партнёров идут напрямую в MES API и в Метрику не попадают совсем. О проблемах мы узнаём от клиентов, когда заказ уже просрочен.

Что даст мониторинг:

- Увидим, где застревают заказы. Количество заказов по статусам и состояние очередей RabbitMQ покажут, на каком шаге заказы копятся.
- Узнаем о проблеме раньше клиента. Алерт придёт, когда выросли ошибки или встала очередь, а не когда партнёр напишет жалобу.
- Поймём, почему тормозит MES: из-за расчёта цены, из-за базы или из-за нехватки CPU и памяти.
- Сможем планировать рост. Заказов каждый месяц на 100 больше, плюс заказы через API. По графикам видно, когда закончатся ресурсы и пора добавлять инстансы.
- Сможем измерить результат доработок (асинхронный расчёт, DLQ, кеш): стало лучше или нет.
- Сможем дать партнёрам понятный SLA (время ответа, доля ошибок) и проверять, что мы его выполняем.

Для бизнеса: компания уже потеряла несколько крупных контрактов из-за проблем с заказами. Мониторинг строим на бесплатных open-source инструментах (Prometheus, Grafana). Нужны одна виртуальная машина и примерно 2–3 недели работы DevOps и разработчиков. Это дешевле одного потерянного контракта.

## 2. Выбор подхода к мониторингу

- **RED** (Rate, Errors, Duration) — для Shop API, CRM API и MES API. Покупателю и партнёру важно одно: сколько запросов проходит, сколько с ошибкой и как быстро приходит ответ.
- **USE** (Utilization, Saturation, Errors) — для ресурсов: виртуальных машин с API, Shop DB, MES DB, RabbitMQ и S3. Тут важно, не заканчиваются ли CPU, память, соединения и место.
- **Бизнес-метрики заказов** — их нет ни в RED, ни в USE, но именно они отвечают на главный вопрос: «где сейчас заказ».

«Четыре золотых сигнала» отдельно не берём: RED и USE вместе их покрывают (latency, traffic, errors, saturation). Так проще делить ответственность: разработчики смотрят на RED, DevOps — на USE.

## 3. Метрики

Правило для ярлыков: не делаем ярлыки с большим количеством значений (id заказа, id покупателя), иначе Prometheus раздувается. Такие вещи ищем в логах и трейсинге.

### 3.1. API (RED)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Number of requests (RPS) for shop API | Нагрузка от покупателей и её рост. Если RPS упал до нуля — магазин не работает | endpoint, method, status |
| Number of requests (RPS) for CRM API | Нагрузка от продавцов | endpoint, method, status |
| Number of requests (RPS) for MES API | Основная нагрузка: операторы и партнёры | endpoint, method, status, client_type (operator / partner) |
| Number of requests (RPS) per user for MES API | Видно, какой партнёр сколько нагружает MES. Пригодится для лимитов и разговора с партнёром | partner_id (партнёров немного, ярлык не раздуется) |
| Number of HTTP 200 / HTTP 500 for shop, CRM, MES API | Доля ошибок = 500 / все запросы. По ней ставим алерт. Отдельные метрики не заводим: это тот же счётчик запросов с ярлыком status | endpoint, method, status |
| Response time (latency) for shop, CRM, MES API | Скорость ответа. Для MES — это медленный дашборд у операторов и таймауты у партнёров. Смотрим p50, p95, p99 | endpoint, method |

Что не берём:

- RPS per user для shop API — покупателей много, ярлык user_id раздует метрики. Если понадобится, посмотрим в логах.
- RPS per user для CRM API — продавцов несколько человек, пользы мало.
- Number of simultaneous sessions — аутентификацию по условию не трогаем, нагрузку и так видно по RPS и соединениям к базе.
- Kb transferred / provided — сеть сейчас не узкое место, а объём файлов видно по размеру S3.

### 3.2. Ресурсы (USE)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| CPU % for shop, CRM, MES API | Загрузка инстанса. Для MES самая важная: расчёт цены забирает CPU, и тормозит всё остальное | service, instance |
| Memory Utilisation for shop, CRM, MES API | Утечки памяти и риск падения по нехватке памяти | service, instance |
| CPU % for shop db, MES db (нет в списке, добавляем) | Без него не понять, тормозит ли база (например, на дашборде MES) | instance |
| Memory Utilisation for shop db, MES db | Если памяти мало, запросы идут на диск и замедляются | instance |
| Number of connections for shop db, MES db | Shop DB используют два приложения. Если одно заберёт все соединения, встанут оба | instance, application (shop-api / crm-api) |
| Size of shop db, MES db | Рост данных, чтобы заранее увеличить диск | instance |
| Size of S3 storage | 3D-модели тяжёлые, хранилище растёт, а это деньги | bucket |

### 3.3. RabbitMQ

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Number of dead-letter-exchange letters | Каждое сообщение в DLQ — заказ, который не обработался. Главная метрика для «потерянных» заказов | queue |
| Number of messages in flight | Сообщения взяты в работу, но не подтверждены. Если число растёт — обработчик завис | queue |
| Количество сообщений в очереди (добавляем) | Очередь растёт — обработчик не успевает или упал | queue |
| Количество consumers (добавляем) | Если consumers = 0, сообщения никто не читает | queue |

### 3.4. Бизнес-метрики (добавляем сами)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Количество заказов в каждом статусе | Видно, где копятся заказы. Например, много заказов в SUBMITTED — значит, не считается цена | status, source (shop / api) |
| Количество зависших заказов (в статусе дольше нормы) | Сразу показывает проблемные заказы. Например, SUBMITTED дольше 1 часа, хотя расчёт занимает максимум 30 минут | status, source |
| Время расчёта цены в MES | Расчёт длится от 2 до 30 минут. Видно, когда он тормозит и сколько мощности нужно | source |
| Количество новых заказов | Замена Яндекс Метрике для заказов через API, видно рост | source |

## 4. План действий

1. Создать виртуальную машину для мониторинга. Развернуть на ней Prometheus (time-series база для метрик), Grafana (дашборды) и Alertmanager (алерты). Хранить метрики 30 дней.
2. Поставить node_exporter на машины с Shop API, CRM API и MES API, чтобы собирать CPU и память.
3. Shop API и CRM API (Spring Boot): подключить Actuator и Micrometer, открыть `/actuator/prometheus`, добавить ярлыки endpoint, method, status.
4. MES API (C#): подключить библиотеку prometheus-net, открыть `/metrics`. Добавить ярлыки client_type и partner_id и метрику времени расчёта цены.
5. RabbitMQ: включить плагин `rabbitmq_prometheus`. Если DLQ ещё не настроена — настроить (инициатива из задания 1).
6. Shop DB, MES DB и S3: забирать метрики из Yandex Monitoring (managed-сервисы отдают их сами) или поставить postgres_exporter.
7. Бизнес-метрики: в CRM API и MES API добавить задачу, которая раз в минуту считает заказы по статусам и зависшие заказы и отдаёт результат в метрики.
8. Сделать дашборды в Grafana: по одному на каждое API (RED), инфраструктура (USE), RabbitMQ, заказы.
9. Настроить алерты в рабочий чат и на почту, для критичных — звонок дежурному.
10. Закрыть доступ: в Grafana входят только сотрудники с учётной записью, Prometheus и `/metrics` доступны только из внутренней сети.
11. Показать дашборды команде и продакт-менеджеру, договориться, кто и как реагирует на алерты.

## 5. Дополнительно: пороги насыщенности

У нас по одному инстансу на всё, подстраховки нет, поэтому пороги ставим с запасом — чтобы успеть отреагировать до падения.

Реакции:
- **Чат** — сообщение в рабочий чат команды.
- **Тикет** — задача в трекере на разбор.
- **Звонок** — автоматический звонок дежурному.

| Показатель | Порог | Почему | Что делаем |
|---|---|---|---|
| CPU API | > 80% дольше 10 минут | Остаётся запас на пики нагрузки | Чат и тикет. Если повторяется регулярно — добавляем инстанс |
| Память API | > 85% дольше 10 минут | Дальше приложение может упасть | Чат и тикет. Если > 95% — звонок |
| Соединения к БД | > 80% от max_connections | При 100% новые запросы падают. Для Shop DB — сразу в двух приложениях | Чат и тикет, проверить пул соединений |
| Память БД | > 85% | Запросы начинают тормозить | Тикет, увеличить класс инстанса |
| Диск БД | > 80% | При заполненном диске база перестаёт принимать запись | Тикет, увеличить диск |
| Сообщения в очереди RabbitMQ | Растут 15 минут подряд или consumers = 0 | Заказы перестали обрабатываться | Звонок |
| Messages in flight | Не уменьшаются 15 минут | Обработчик завис | Чат и тикет |

Кроме насыщенности, ставим алерты на:
- DLQ > 0 — чат и тикет сразу.
- Доля HTTP 500 > 1% за 5 минут — звонок.
- Зависшие заказы > 0 — тикет в поддержку, менеджер связывается с клиентом.
